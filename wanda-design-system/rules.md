# Wanda — правила роботи з Figma-лейаутами

## Брейкпоінти (xs / sm / md / lg / xl)

1. Горизонтальна відстань між сусідніми фреймами брейкпоінтів — завжди рівно **200px**.
2. Коли рядок/грід (напр. Stats row, Cards) переводиться на `layoutWrap="WRAP"` для рефлоу під вужчі брейкпоінти —
   обов'язково задавати `counterAxisSpacing`, рівним `itemSpacing` (гепу між колонками).
   Інакше рядки, що переносяться, злипаються без відступу по вертикалі.

## Сторінкові лейаути (page-level grid) — на основі аналізу "Lobby — Authorized"

Еталонна збірка: файл `QbmTYjRSyzALRb5GIl4Itk` ("W" — Main), node `8991:58214`, усі 5 брейкпоінтів (xs/sm/md/lg/xl).

### Вертикальний ритм — не залежить від брейкпоінта
1. Гап між сусідніми секціями сторінки (Wrapper→Wrapper) — завжди рівно **16px** на всіх брейкпоінтах.
2. Гап Heading → контент секції: **8px** на xs/sm/md, **12px** на lg/xl (heading при цьому росте з 32px до 40px).
3. Top padding контейнера перед першою секцією: xs=4px, sm=8px, md/lg/xl=16px.

### Горизонтальні падінги — НЕ масштабуються лінійно з шириною! Завжди звіряти по факту, не екстраполювати
| Breakpoint | Ширина Page-container | Side padding секції |
|---|---|---|
| xs | 360 | 16px |
| sm | 768 | 40px |
| md | 1024 | 40px |
| lg | 1280 | 36px |
| xl | 1360 | 32px (додатковий шар padding на рівні `Container`, якого нема на md/lg) + 36px на рівні секції |

xl — виняток: тут з'являється додатковий рівень padding на `Container` (32px) поверх стандартного секційного (36px). На md/lg такого немає — там `Container` без бічних падінгів, все падить на рівні секції.

### Гапи всередині карткових рядів — фіксовані 8px, не масштабуються
Card/Activities, event, Card/Tournament, Card/Default — гап між картками = **8px на всіх брейкпоінтах**, незалежно від ширини картки.

### Card/Default — патерн "fixed-size grid"
Розмір картки фіксований **200×112 на будь-якому брейкпоінті** (не масштабується). Замість resize — змінюється кількість карток у рядку: xs=2, sm=4, md=4, lg=6, xl=8.

### Загальна структура сторінки (md/lg/xl)
`Header` → `Wrapper` (Sidebar 80px fixed + Page-container) → `Hero` → `Body` → `Container` (top padding) → N × секція `Wrapper` (Heading + контент, гап 16px між секціями) → `Footer`.
На xs/sm сайдбару немає, Header на всю ширину, Hero одразу під Header (без обгортки Wrapper з сайдбаром).

## Додавання нового контенту (Wanda design system)

1. Використовувати ВИКЛЮЧНО компоненти з дизайн-системи — instance реальних компонентів
   через `getMainComponentAsync` / `importComponentSetByKeyAsync` / `search_design_system`.
   Не малювати імітації вручну через fills/rectangles.
2. Кольори — тільки токени/змінні дизайн-системи. Не хардкодити нові hex-кольори
   (в т.ч. не використовувати чорний `#000000`/near-black для нових карток/блоків,
   якщо це не існуючий токен).
3. Шрифти — тільки ті, що вже задані в ДС (Bungee для заголовків, Open Sans для тексту)
   з правильними style-неймами.
4. Увесь текстовий контент (заголовки, лейбли, кнопки, плейсхолдери) — завжди англійською
   мовою, незалежно від мови запиту в чаті.

## Візуальні баги, знайдені при аналізі лейаутів

Коли Claude звіряє готовий лейаут із правилами вище (breakpoint-аналіз) і знаходить відхилення, яке візуально виглядає як **помилка збірки**, а не навмисне рішення — таке відхилення фіксується тут окремим пунктом, а не додається як нове "правило" (бо це не стандарт, а known issue для перевірки/фіксу).

Формат запису: компонент/сторінка → який брейкпоінт → в чому відхилення → з чим звіряли.

## Процес аналізу лейауту — завжди з виправленою версією

Коли Claude робить аналіз готового лейауту на відповідність правилам (breakpoint-звірка) і знаходить відхилення/баг:
1. Не обмежуватись текстовим описом — одразу створити в тому ж Figma-файлі (поруч із оригінальним фреймом, з відступом, без зміни оригіналу) виправлену копію проблемного фрейму/секції з застосованим фіксом.
2. Дати обидва nodeId/посилання — оригінал і виправлений варіант — щоб користувач міг порівняти візуально (напр. через скрін або side-by-side).
3. Текстовий опис (що саме поправлено) додається як підпис до виправленої версії, а не замінює її.

## Нейминг шарів під час технічного ревю

Роблячи технічне ревю лейауту (breakpoint-звірка чи будь-яка інша перевірка макета), Claude одразу перейменовує всі шари-автолейаути на `Wrapper` — не чекаючи окремого запиту користувача і не обмежуючись коментарем "перейменуй тут". Це правило нейминга (див. чеклист "Підготовка макетів" вище), яке застосовується проактивно в межах самого ревю.

## Процес роботи з документами (Чорновик → Чистовик)

### Термінологія
- **⚫️ Чорновик** — окремий документ у проєкті "Worklog". Для попереднього затвердження концепту Дімою/Колею/Замовником. НЕ зобов'язаний мати всі брейкпоінти/стани/компоненти.
- **⚪️ Чистовик** — зміни, перенесені в бренчу відповідного документа з "Sitemap". Зобов'язаний мати всі брейкпоінти, бути зібраним виключно на компонентах/токенах/стилях бібліотеки.

### Стадії роботи з документами
1. ⚫️ Чорновик — Wanda review (внутрішній груммінг/рев'ю командою Wanda)
2. ⚫️ Чорновик — CD/HD review (затвердження концепту, UI/UX)
3. ⚫️ Чорновик — First customer review
4. ⚪️ Чистовик — Technical review
5. ⚪️ Чистовик — Second customer review (фінальне затвердження замовником)

### Перехід на ⚪️ Чистовик
- У відповідному документі з "Sitemap" створюємо бренчу з назвою `Updates [номер]` (у квадратних дужках — тільки номер задачі, без префіксу "YDW-").
- Якщо бренча `Updates [***]` вже існує в цьому документі — переносимо зміни в неї і дописуємо свій номер задачі через слеш (`Updates [123/456]`).

### Підготовка до Technical Review

**Підготовка компонентів**
- Коректний нейминг (Sentence case; Parent/Child)
- Відсутність нецілих значень
- Логічні й інтуїтивні назви властивостей та їх значень
- Правильний порядок властивостей і значень (від частих до рідких, від більшого до меншого)
- Boolean-формат властивості, коли доступно лише 2 значення
- Видалити властивості, у яких доступне лише 1 значення
- Відповідність назви властивості й шару, до якого вона застосовується
- Відповідність порядку властивостей і шарів
- Відсутність граматичних помилок у назвах компонентів/властивостей/значень/шарів/токенів
- Заблокувати шари/instance, до яких треба обмежити доступ
- Коректна відпрацювання всіх комбінацій властивостей
- Коректне "розтягування/звуження" компонента, якщо це передбачено
- Коректна поведінка тексту при вводі довгих слів/словосполучень/речень
- Прив'язка елементів компонента до відповідних токенів (з урахуванням варіантів/станів/форм)
- Відсутність "зламаних" токенів
- Відсутність прив'язок через стиль або змінну (лише токени)
- Перевикористовувати нейминг-патерни раніше створених компонентів
- Автоматична калькуляція значень, де можливо
- Позиціонувати всі компоненти відносно 0-координати
- Вирівняти варіанти всередині component set
- Залишити увімкненими тільки ті властивості, що використовуються за замовчуванням
- ⚠️ Використовувати префікс `v2/v3` у назвах токенів для підтримки старого й нового набору

**Підготовка макетів**
- Підтягнути всі зміни з бібліотек
- Позбутись зайвих бібліотек і модів із них
- Відсутність component-змінних у списку доступних
- Позбутись сміття
- Позиціонувати всі секції відносно 0-координати
- Згрупувати всі локальні компоненти в одну секцію (крім контенту для модалок/дроверів)
- Кожен макет — усі брейкпоінти згруповані в секцію з інтуїтивною назвою
- Підготувати всі стани компонентів (у розумних межах; опційно)
- Дистанція **600px** між секціями
- Дистанція **80px** між макетами/локальними компонентами всередині секції
- Забезпечити макети картинками
- Збірка макетів виключно на токенах/змінних/стилях/компонентах бібліотеки
- Коректний нейминг усіх шарів — усі автолейаут-фрейми називати `Wrapper`
- Відсутність зайвих фреймів/врапперів у макетах
- Відсутність зламаних компонентів
- Безпроблемний своп бібліотек

### Синхронізація / DS Sync (🚨 обрати один варіант)
- Вручну переносимо зміни у разі часткової реалізації задач
- Або призупиняємо синхронізацію макетів до виконання всіх наслоєних задач у бренчі

### FAQ
**Коли видаляти ⚫️ Чорновик?**
Тільки після абсолютної готовності ⚪️ Чистовика — коли всі зміни перенесені. Залишити посилання на ⚪️ Чистовик у самій задачі (в Jira).

**Як зберегти "корисні" напрацювання з ⚫️ Чорновика перед видаленням?**
Створити новий документ, перенести туди все потрібне, і лише тоді видалити чорновик (чорновик ОБОВ'ЯЗКОВО має перестати існувати, щоб уникнути помилок при передачі макетів розробникам).

## Процес оновлення цього файлу

Кожна зміна в rules.md комітиться в цей репозиторій і йде в основну гілку
(за бажанням — через Pull Request для рев'ю). Колеги отримують оновлення через `git pull`.

## Редагування компонентів

Файли компонентів у `references/*.md` (включно з `card/*.md`) — це задокументований опис реального стану дизайн-системи в Figma. Claude НЕ РЕДАГУЄ ці файли самостійно за власною ініціативою. Будь-яка зміна в reference-файлі компонента вноситься лише за прямим запитом користувача з чітким описом, що саме змінилось у Figma (новий варіант, токен, стан тощо), і завжди звіряється з актуальним `get_design_context`/`search_design_system`, а не пишеться "з пам'яті".
