# Wanda — правила роботи з Figma-лейаутами

## Брейкпоінти (xs / sm / md / lg / xl)

1. Горизонтальна відстань між сусідніми фреймами брейкпоінтів — завжди рівно **200px**.
2. Коли рядок/грід (напр. Stats row, Cards) переводиться на `layoutWrap="WRAP"` для рефлоу під вужчі брейкпоінти —
   обов'язково задавати `counterAxisSpacing`, рівним `itemSpacing` (гепу між колонками).
   Інакше рядки, що переносяться, злипаються без відступу по вертикалі.

## Сторінкові лейаути (page-level grid) — на основі аналізу "Lobby — Authorized"

Еталонна збірка: файл `QbmTYjRSyzALRb5GIl4Itk` ("W" — Main), node `8991:58214`, усі 5 брейкпоінтів (xs/sm/md/lg/xl).

### Вертикальний ритм — не залежить від брейкпоінта
1. Гап між сусідніми секціями сторінки (Wrapper→Wrapper) — завжди рівно **16px** на всіх брейкпоінтах.
2. Гап Heading → контент секції: **8px** на xs/sm/md, **12px** на lg/xl (heading при цьому росте з 32px до 40px).
3. Top padding контейнера перед першою секцією: xs=4px, sm=8px, md/lg/xl=16px.

### Горизонтальні падінги — НЕ масштабуються лінійно з шириною! Завжди звіряти по факту, не екстраполювати
| Breakpoint | Ширина Page-container | Side padding секції |
|---|---|---|
| xs | 360 | 16px |
| sm | 768 | 40px |
| md | 1024 | 40px |
| lg | 1280 | 36px |
| xl | 1360 | 32px (додатковий шар padding на рівні `Container`, якого нема на md/lg) + 36px на рівні секції |

xl — виняток: тут з'являється додатковий рівень padding на `Container` (32px) поверх стандартного секційного (36px). На md/lg такого немає — там `Container` без бічних падінгів, все падить на рівні секції.

### Гапи всередині карткових рядів — фіксовані 8px, не масштабуються
Card/Activities, event, Card/Tournament, Card/Default — гап між картками = **8px на всіх брейкпоінтах**, незалежно від ширини картки.

### Card/Default — патерн "fixed-size grid"
Розмір картки фіксований **200×112 на будь-якому брейкпоінті** (не масштабується). Замість resize — змінюється кількість карток у рядку: xs=2, sm=4, md=4, lg=6, xl=8.

### Загальна структура сторінки (md/lg/xl)
`Header` → `Wrapper` (Sidebar 80px fixed + Page-container) → `Hero` → `Body` → `Container` (top padding) → N × секція `Wrapper` (Heading + контент, гап 16px між секціями) → `Footer`.
На xs/sm сайдбару немає, Header на всю ширину, Hero одразу під Header (без обгортки Wrapper з сайдбаром).

## Додавання нового контенту (Wanda design system)

1. Використовувати ВИКЛЮЧНО компоненти з дизайн-системи — instance реальних компонентів
   через `getMainComponentAsync` / `importComponentSetByKeyAsync` / `search_design_system`.
   Не малювати імітації вручну через fills/rectangles.
2. Кольори — тільки токени/змінні дизайн-системи. Не хардкодити нові hex-кольори
   (в т.ч. не використовувати чорний `#000000`/near-black для нових карток/блоків,
   якщо це не існуючий токен).
3. Шрифти — тільки ті, що вже задані в ДС (Bungee для заголовків, Open Sans для тексту)
   з правильними style-неймами.
4. Увесь текстовий контент (заголовки, лейбли, кнопки, плейсхолдери) — завжди англійською
   мовою, незалежно від мови запиту в чаті.

## Візуальні баги, знайдені при аналізі лейаутів

Коли Claude звіряє готовий лейаут із правилами вище (breakpoint-аналіз) і знаходить відхилення, яке візуально виглядає як **помилка збірки**, а не навмисне рішення — таке відхилення фіксується тут окремим пунктом, а не додається як нове "правило" (бо це не стандарт, а known issue для перевірки/фіксу).

Формат запису: компонент/сторінка → який брейкпоінт → в чому відхилення → з чим звіряли.

### Приклад: "Game mood for VIP" — зайвий top-gap на xl
Файл `qgI92gvFH3ZYQMJxcCVhjn`, node `37280:162393` (xl) vs `37280:162434` (lg).
На lg/md/sm верхній `Container` (з градієнтом-хедером секції) стоїть впритул до Body (top-margin=0px).
На xl — той самий `Container` має top-margin **32px**, через що зелений градієнт відходить від хедера сторінки помітним зазором (видно на порівняльному скріні lg/xl).
На xs — теж є розбіжність, top-margin **24px** замість очікуваних 0px.
Звірено метаданими Figma (`get_metadata`) по всіх 5 брейкпоінтах: sm/md/lg = 0px, xs = 24px, xl = 32px — це непослідовний патерн, що вказує на помилку саме в крайніх брейкпоінтах (xs, xl), а не на навмисне дизайн-рішення.

## Процес аналізу лейауту — завжди з виправленою версією

Коли Claude робить аналіз готового лейауту на відповідність правилам (breakpoint-звірка) і знаходить відхилення/баг:
1. Не обмежуватись текстовим описом — одразу створити в тому ж Figma-файлі (поруч із оригінальним фреймом, з відступом, без зміни оригіналу) виправлену копію проблемного фрейму/секції з застосованим фіксом.
2. Дати обидва nodeId/посилання — оригінал і виправлений варіант — щоб користувач міг порівняти візуально (напр. через скрін або side-by-side).
3. Текстовий опис (що саме поправлено) додається як підпис до виправленої версії, а не замінює її.

## Редагування компонентів

Файли компонентів у `references/*.md` (включно з `card/*.md`) — це задокументований опис реального стану дизайн-системи в Figma. Claude НЕ РЕДАГУЄ ці файли самостійно за власною ініціативою. Будь-яка зміна в reference-файлі компонента вноситься лише за прямим запитом користувача з чітким описом, що саме змінилось у Figma (новий варіант, токен, стан тощо), і завжди звіряється з актуальним `get_design_context`/`search_design_system`, а не пишеться "з пам'яті".
